# NEKalkan и оригинальный Калкан: подробное сравнение

Оригинал здесь — `KalkanCrypt.dll` из SDK НУЦ РК 2.0 (Windows x64). NEKalkan сознательно повторяет её поведение там, где это
важно для прикладного кода (коды возврата, форматы, тексты отчётов), и сознательно расходится там, где оригинал небезопасен,
неудобен или падает. Каждое утверждение ниже проверено сверкой с настоящей библиотекой.

## 1. Как проверялось

| Проверка | Что сравнивается |
|---|---|
| Взаимная проверка подписей | подпись NEKalkan проверяет Калкан, подпись Калкана проверяет NEKalkan: CMS (вложенная, отделённая, несколько подписей), RAW, XML (все режимы канонизации); ключи ГОСТ 2015 (256 и 512 бит) и RSA из тестового набора SDK |
| Коды возврата | более 100 сценариев состояния хранилища (какие УЦ загружены), срока сертификата, формата входа и флагов |
| Дифференциальный перебор флагов | случайные сочетания флагов для `HashData`, `SignData`, `VerifyData`, `X509ExportCertificateFromStore`, `X509CertificateGetInfo` (1500 итераций), результаты сопоставляются |
| XML | 252 сочетания флагов канонизации × три документа × два режима выбора узла; 7 вариантов родительского узла и пространства имён |
| Режимы проверки CMS | вложенная/отделённая подпись × флаги `KC_DETACHED_DATA`/`KC_IN2_BASE64` × пять вариантов данных |
| Отзыв сертификатов | до 28 сертификатов (действующие и отозванные) × все CRL из SDK |
| Свойства сертификатов | все 33 свойства `KC_CERTPROP_*` на 48 сертификатах (код возврата и текст) |

## 2. Что совпадает с Калканом

**Подпись и проверка**
* Формат CMS: `SignedData`, CAdES-BES, `signingCertificateV2`, порядок атрибутов, `digestAlgorithms`; отделённая и вложенная подпись, несколько подписей в одном CMS.
* Подпись «готового хэша» (`SignHash`) в режимах RAW и CMS — в том числе то, что `SignHash` не требует загруженных УЦ.
* Правила данных при проверке CMS: без флага `KC_DETACHED_DATA` берётся вложенное содержимое, а переданные данные игнорируются; с флагом проверяются именно переданные данные, даже если в CMS есть своё содержимое; отделённая подпись без флага — `0x2E06307F`.
* Отчёт проверки: `Signature N 1`, `- CAdES-BES: verify signer certificate hash - OK.`, `Verify - OK`, `CMS Verify - OK`; у отделённой подписи — без завершающего перевода строки, как у Калкана.

**XML**
* Структура `ds:Signature` совпадает с оригиналом до символа (отличаются только значения дайджеста, подписи и сертификат): `Id="1"`, `CanonicalizationMethod`, `SignatureMethod`, `Reference`, `Transforms`, `KeyInfo/X509Data`.
* Все флаги канонизации `KC_XML_*` и `KC_XMLC_*`, подпись всего документа или узла по `Id`, вставка подписи в заданный родительский элемент (в том числе с пространством имён и случаем «родитель не найден»).
* Несколько подписей в одном документе: каждая следующая подписывает документ вместе с предыдущими.
* Отчёт `VerifyXML`: `Signature N`, `Id =`, серийный номер, алгоритм, ИИН/БИН, `Signature is OK`.

**Сертификаты**
* Все свойства `KC_CERTPROP_*` — тот же текст (`CN=…`, `serialNumber=IIN…`, `notAfter=дд.мм.гггг чч:мм:сс` …); для отсутствующего атрибута имени — `KCR_GETCERTPROPERR` (`0x08F00038`), для неизвестного свойства — `KCR_INVALID_PROPID`.
* Экспорт сертификата в DER/PEM/Base64, разбор входного сертификата в любом из этих видов.
* Отзыв по CRL: `KCR_LOADCRLERROR` (CRL выпущен не издателем сертификата), `KCR_CRLEXPIRED` (срок CRL проверяется всегда, `KC_NOCHECKCERTTIME` на него не влияет), `KCR_CERT_STATUS_REVOKED`.

**Состояние и ошибки**
* Без загруженного издателя подпись, проверка и `X509ValidateCertificate` дают `KCR_CACERTNOTFOUND` (`0x08F00040`); `VerifyXML` без набора УЦ — `KCR_LOADTRUSTEDCERTSERR` (`0x08F00022`).
* Просроченный сертификат — `0x08F00042`; неверный пароль — `0x08F00009`; нет файла контейнера — `0x08F00003`; неверная длина хэша — `0x08F0004B`; пустые флаги подписи — `0x08F0001A`; нет режима подписи — `0x08F00039`.
* Ошибки проверки подписи — коды OpenSSL, как у Калкана: `0x8006E07B` (ГОСТ), `0x2E09A09E` (CMS), `0x0D0680A8` (ASN.1) и тексты вида `error:2E09A09E:CMS routines:…`.
* `KC_USE_CRL`, `KC_NOCHECKCERTTIME`, `checkTime` в `X509ValidateCertificate` (параметр, как и у оригинала, не влияет на результат — проверка идёт на текущий момент).

## 3. Где NEKalkan строже и безопаснее

| Ситуация | Калкан | NEKalkan |
|---|---|---|
| Загружен промежуточный сертификат, корня нет | подпись и проверка данных проходят | `KCR_CHECKCHAINERROR` (`0x08F0000E`) — доверие требует корня (`X509ValidateCertificate` у Калкана даёт тот же код) |
| Некорректный Base64 на входе | при подписи данных мусор молча превращается в данные | `KCR_BASE64_DECODE_ERROR`; допускаются только `A–Z a–z 0–9 + /`, `=` в конце, переводы строк |
| Несогласованные флаги и данные | процесс может аварийно завершиться (`VerifyData` с произвольными сочетаниями флагов) | всегда код ошибки; поведение проверено фаззингом (десятки тысяч мутаций CMS, XML, PKCS#12, сертификатов) и тестами враждебных входов |
| Подпись XML-документа, в котором уже есть «заготовка» `ds:Signature` с пустым `SignatureValue` | принимает | отклоняется (`KCR_XMLSETSIGNERROR`): иначе можно подписать чужой `SignedInfo` |
| Два элемента с одинаковым `Id` | подпись такого узла отклоняется (`0x08F00027`) | то же; кроме того, при проверке ссылка на неоднозначный `Id` считается недействительной (защита от подмены узла) |
| Подпись узла, внутри которого стоит сама подпись | подпись получается невалидной: при проверке она входит в собственный дайджест (проверка оригинальной подписи тем же Калканом даёт `0x08F00023`) | автоматически добавляется преобразование `enveloped-signature`; такая подпись проверяется |
| `Id` подписи совпадает с `Id` чужого элемента | возможен | номер подбирается так, чтобы не пересекаться с существующими `Id` |
| Нехватка памяти при проверке | не документировано | ошибка `KCR_MEMORY_ERROR`, а не «успех» с частичной проверкой |
| Ключи малого порядка в сертификате, RSA-экспонента `e < 3` | не проверялось | проверка подписи отвергает |
| Глубокая вложенность, миллионы атрибутов, раздутый ASN.1/BER | не проверялось | предельная глубина XML 256, не более 4096 атрибутов и 512 объявлений пространств имён на элемент, ограничения на размеры ASN.1 |
| Закрытый ключ в памяти | не документировано | затирается при `Finalize` и при удалении объекта |

## 4. Где поведение намеренно иное

| | Калкан | NEKalkan |
|---|---|---|
| Состояние | глобальное на процесс: загрузка ключа и сертификатов одним объектом видна всем остальным, `Finalize` гасит все | каждый объект компоненты имеет свой контекст: свой ключ, свои УЦ, свой журнал ошибок |
| Пути к файлам | однобайтовые (ASCII); путь с кириллицей приходится заменять копией | любые: Unicode, абсолютные пути длиннее 260 символов |
| Кодировка строк в 1С | `ACP` по умолчанию | `UTF-8` по умолчанию; строка, не представимая в выбранной кодировке, — ошибка до подписи |
| Двоичные результаты (DER, хэш без Base64) | строка с перекодированными байтами | `ДвоичныеДанные`, байты не искажаются |
| Просроченный УЦ из тестовых наборов при `KC_NOCHECKCERTTIME` | подпись отклоняется (`0x08F00040`) | подписывает, так как флаг отключает проверку сроков всей цепочки |
| Бит `0x100` в флагах XML | совпадает с `KC_WITH_TIMESTAMP`: при `KC_XMLC_INCL_C14N11` Калкан пытается идти на TSA и без сети отвечает `0x08F00047` | `KC_XMLC_INCL_C14N11` работает как канонизация; метка времени запрашивается только флагом `KC_WITH_TIMESTAMP` (в версии 1.0 — отказ) |
| Ключ ГОСТ 2001 | подпись и проверка | загрузка даёт `KCR_UNKNOWN_ALG`; подписи таких ключей проверяются |
| Служебные методы `SetKalkanPath`, `SetKeyStoreTempDirectory` | указывают на DLL и каталог временных файлов | принимаются и игнорируются (DLL и временных файлов нет) |

## 5. Чего в NEKalkan 1.0 нет

* Аппаратные токены и ID-карты (`GetTokens`, типы хранилищ, отличные от `KCST_PKCS12`).
* Запросы по сети: метка времени TSA, OCSP, загрузка CRL по адресу, прокси (`SetProxy` принимает параметры, но сети нет).
* `SignWSSE`, `ZipConSign`, `ZipConVerify`, `GetCertFromZipFile` (возвращают `WRAP_NOT_IMPLEMENTED`).
* Чтение системного хранилища сертификатов Windows: доверенные сертификаты загружаются явно.
* Подпись ключами ГОСТ 34.10-2001.

## 6. Скорость

Измерено на одном ядре, ключ ГОСТ 512 бит, вызовы через один и тот же слой (миллисекунды, меньше — лучше):

| Операция | Калкан | NEKalkan |
|---|---|---|
| CMS: подпись небольших данных | 3,0 | 5,3 |
| CMS: проверка | 4,2 | 6,5 |
| XML: подпись небольшого документа | 3,1 | 5,3 |
| XML: проверка | 12,1 | 6,5 |
| Стрибог-512, 30 МБ | 158 | 144 |

Подпись у NEKalkan на 2 мс медленнее, проверка XML вдвое быстрее. Для документооборота разница не заметна;
при пакетной подписи NEKalkan не использует временных файлов и внешних процессов.
Большие данные: хэш 30 МБ — 0,14 с (≈ 210 МБ/с), CMS-подпись 30 МБ — 0,36 с, подпись XML 6 МБ — 0,6 с.

## 7. Как перейти с Калкана

1. Подключить `NEKalkan_win64.zip` вместо компоненты на `KalkanCrypt.dll`; заменить `AddIn.<имя>.KalkanCrypt` на `AddIn.<имя>.NEKalkan`.
2. Убрать вызовы `SetKalkanPath`, `SetKalkanDirectory`, `SetKeyStoreTempDirectory` (можно оставить — они ничего не делают).
3. Загрузить корневой и промежуточный сертификаты НУЦ через `X509LoadCertificateFromFile/Buffer` (в Калкане то же самое).
4. Если строки с кириллицей раньше подписывались без `SetStringEncoding`, добавить `SetStringEncoding("CP1251")` — иначе байты подписываемых данных изменятся (или перейти на UTF-8 осознанно).
5. Если код использует `SignWSSE`, ZIP-контейнеры, токены или онлайн-проверку отзыва — эти возможности пока остаются на Калкане.
