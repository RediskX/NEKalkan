# NEKalkan — справочник методов

Все методы доступны под английским и русским именем (`SignData` / `ПодписатьДанные`). Названия методов, порядок параметров, флаги и коды ошибок
повторяют Калкан (КалканКрипт НУЦ РК), поэтому знакомый с ним код переносится без переделки. В каждом разделе отмечено, чем NEKalkan отличается от оригинала
(подробное сравнение — [СРАВНЕНИЕ_С_КАЛКАНОМ.md](СРАВНЕНИЕ_С_КАЛКАНОМ.md)). Параметры, отмеченные **↩**, — выходные (передаются по ссылке: переменная
1С получает результат). Параметры, отмеченные **[=""]**, можно опустить.

Условные обозначения: «Данные» — строка 1С (кодируется по `SetStringEncoding`) или `ДвоичныеДанные`; «Код» — число `KCR_*`/`WRAP_*`,
`0` — успех.

## 3. Ключ и сертификаты

### LoadKeyStore / LoadKeyStoreSafe (№ 5, 28)

`LoadKeyStore(Тип, Пароль, Контейнер, Алиас [=""])` → Код

* `Тип` — `KCST_PKCS12` (единственный поддерживаемый; прочие — `KCR_NOTOKENFOUND`).
* `Контейнер` — путь к файлу `.p12` (любые символы Unicode).
* `Алиас` — не используется.

Определяется формат: ГОСТ 2015 (256/512 бит, любой из порядков байт ключа — выбирается проверкой по открытому ключу
сертификата), ГОСТ 2001, RSA. Пароль PKCS#12 проверяется по MAC. Коды: `KCR_ERROR_OPEN_PKCS12` (файл не открылся),
`KCR_INVALIDPASSWORD`, `KCR_ERROR_READ_PKCS12`, `KCR_KEY_NOT_FOUND`.

**Как у Калкана:** коды `KCR_ERROR_OPEN_PKCS12`, `KCR_INVALIDPASSWORD`, `KCR_KEY_NOT_FOUND`. **Отличия:** путь может быть любым (Unicode, длиннее 260 символов), без временных
копий ключа; ключи ГОСТ 2001 («2004») и устаревшие схемы НУЦ дают `KCR_UNKNOWN_ALG` (Калкан их загружает); токены не поддерживаются.

### X509LoadCertificateFromFile (№ 31) / X509LoadCertificateFromBuffer (№ 32)

`X509LoadCertificateFromFile(Путь, Тип)` и `X509LoadCertificateFromBuffer(Сертификат, Тип)` → Код

`Тип`: `KC_CERT_CA` (корневой, доверенный), `KC_CERT_INTERMEDIATE` (промежуточный), `KC_CERT_USER` (сертификат
пользователя — например, для проверки RAW-подписи). Формат — DER, PEM или Base64. Повторная загрузка того же
сертификата безвредна.

**Как у Калкана:** сертификаты хранятся в объекте, а не в системном хранилище; без издателя в хранилище подпись и проверка дают `KCR_CACERTNOTFOUND`.
**Отличие:** хранилище у каждого объекта своё, а не общее на процесс.

### X509ExportCertificateFromStore (№ 6) / ExportCertificate (№ 7)

`X509ExportCertificateFromStore(Алиас, Флаг, Сертификат ↩)` → Код; `ExportCertificate(Алиас, Флаг)` → Строка/BLOB.

`Флаг`: `KC_CERT_DER` (`0x101`, BLOB), `KC_CERT_PEM` (`0x102`), `KC_CERT_B64` (`0x104`) или `KC_OUT_DER/KC_OUT_PEM/KC_OUT_BASE64`.
Экспортируется сертификат загруженного ключа.

### X509CertificateGetInfo (№ 11) / CertificateGetInfo (№ 12)

`X509CertificateGetInfo(Сертификат, Свойство, Значение ↩)` → Код; `CertificateGetInfo(Сертификат, Свойство)` → Строка.

`Сертификат` — DER/PEM/Base64. `Свойство` — одна из `KC_CERTPROP_*` (`0x801`…`0x821`): страна/область/город/организация/CN издателя
и субъекта, ИИН/БИН (`SUBJECT_SERIALNUMBER`), e-mail, сроки действия, использование ключа, SN, DN, алгоритм подписи, открытый ключ, OCSP/CRL-адреса.
Неизвестное свойство — `KCR_INVALID_PROPID`.

**Как у Калкана:** текст свойств, `KCR_INVALID_PROPID` для неизвестного кода, `KCR_GETCERTPROPERR` для отсутствующего атрибута имени.

### X509ValidateCertificate (№ 33) / X509ValidateCertificateResult (№ 34)

`X509ValidateCertificate(Сертификат, ТипПроверки, ПутьПроверки, ВремяПроверки (игнорируется, как у KalkanCrypt: проверка всегда на текущий момент), Флаги, Информация ↩ [=""], ОтветOCSP ↩ [=""])` → Код  
`X509ValidateCertificateResult(Сертификат, ТипПроверки, ПутьПроверки, Флаги)` → Строка (информация).

`ТипПроверки`: `KC_USE_NOTHING` — цепочка до загруженного корня и сроки; `KC_USE_CRL` — дополнительно проверка отзыва по
CRL из **файла** `ПутьПроверки`; `KC_USE_OCSP` — в версии 1.0 возвращает `KCR_OCSP_CONNECTIONERR` (сетевых запросов нет). `Флаги`: `KC_NOCHECKCERTTIME`.
Срок действия самого CRL проверяется всегда (флаг `KC_NOCHECKCERTTIME` на него не действует): истёкший CRL — `KCR_CRLEXPIRED` (`0x08F0005D`);
CRL, выпущенный не издателем сертификата, — `KCR_LOADCRLERROR`; файл не разобран — `KCR_BADCRLFORMAT`. Отозван — `KCR_CERT_STATUS_REVOKED`.

**Как у Калкана:** коды проверки цепочки, срока и CRL (`KCR_LOADCRLERROR`, `KCR_CRLEXPIRED`, `KCR_CERT_STATUS_REVOKED`), параметр `ВремяПроверки` не влияет на результат.
**Отличия:** при одном промежуточном сертификате без корня — `KCR_CHECKCHAINERROR`; онлайн-проверка (OCSP, CRL по адресу) не входит в версию 1.0.

### GetCertificatesList (№ 30), GetTokens (№ 29)

`GetCertificatesList()` → строка (алиас/CN загруженного ключа); `GetTokens(Тип)` → пустая строка, `KCR_NOTOKENFOUND`.

## 4. Хэш

`HashData(Алгоритм, Флаги, Данные, Результат ↩)` → Код; `HashDataResult(Алгоритм, Флаги, Данные)` → Строка/BLOB.

Алгоритм задаётся флагом (приоритет у флага): `KC_HASH_GOST15_512`, `KC_HASH_GOST15_256` (Стрибог), `KC_HASH_GOST95`
(ГОСТ 34.11-94), `KC_HASH_SHA256`; или строкой `Алгоритм` — `"sha256"`, `"Gost34311_95"`. Прочие — `KCR_UNKNOWN_ALG`.
Флаги ввода: `KC_IN_BASE64` (данные — Base64), `KC_IN_FILE` (данные — путь к файлу). Вывод: `KC_OUT_BASE64` — Base64, иначе — BLOB.

**Как у Калкана:** флаги, имена алгоритмов (`"sha256"`, `"Gost34311_95"`), `KCR_UNKNOWN_ALG` для неизвестного алгоритма, ошибка Base64 (`0x08F0001D`) при `KC_IN_BASE64`.

## 5. Подпись данных

`SignData(Алиас, Флаги, Данные, Подпись ↩)` → Код  
`SignDataResult(Алиас, Флаги, Данные, ВходнаяПодпись)` / `SignDataText(…)` → Строка (или BLOB для `KC_OUT_DER`)  
`SignDataBlob(…)` → всегда BLOB  
`SignDataResult3(Алиас, Флаги, Данные)` — без входной подписи.

Флаги:

| Режим | Флаги |
|---|---|
| RAW (чистая подпись) | `KC_SIGN_DRAFT` |
| CMS | `KC_SIGN_CMS` (+ `KC_DETACHED_DATA` — отделённая, без данных внутри) |
| вход | `KC_IN_BASE64` (данные в Base64), `KC_IN_FILE` (данные — путь к файлу) |
| вывод | `KC_OUT_BASE64`, `KC_OUT_PEM`, `KC_OUT_DER` (по умолчанию для CMS без флагов — DER) |
| дополнительно | `KC_NOCHECKCERTTIME` (не проверять срок сертификата подписанта), `KC_WITH_TIMESTAMP` — **не поддерживается** |

Подписант проверяется перед подписью: срок действия и цепочка до загруженных сертификатов НУЦ
(`KCR_CACERTNOTFOUND`, `KCR_CHECKCHAINERROR`, `KCR_CERTTIMEINVALID`).

**Несколько подписей (CMS).** Чтобы добавить вторую подпись, передайте существующую CMS четвёртым параметром
`SignDataResult` с флагом `KC_IN2_BASE64` (если она в Base64) — в результате получится одна CMS с двумя подписантами.
Для detached-подписи данные нужны и при добавлении.

**Как у Калкана:** формат CMS (CAdES-BES), порядок атрибутов, подпись проверяется Калканом; срок и цепочка подписанта проверяются перед подписью; без режима подписи — `0x08F00039`,
при нулевых флагах — `0x08F0001A`. **Отличия:** некорректный Base64 при `KC_IN_BASE64` — ошибка (Калкан подписывает мусор); `KC_WITH_TIMESTAMP` пока не поддерживается.

## 6. Подпись хэша

`SignHash(Алиас, Флаги, Хэш, Подпись ↩)` → Код; `SignHashResult(Алиас, Флаги, Хэш)` → Строка/BLOB.

`Хэш` — готовый дайджест; длина должна равняться длине ключа: 32 или 64 байта для ГОСТ 2015, 32 байта (SHA-256) для RSA; `KC_IN_BASE64` — если хэш в Base64.
`KC_SIGN_DRAFT` — RAW-подпись хэша, `KC_SIGN_CMS` — CMS «по готовому хэшу» (без данных, detached).
Неверная длина — `KCR_INVALID_DIGEST_LEN`.

**Как у Калкана:** `SignHash` не требует загруженных УЦ, длина хэша проверяется (`KCR_INVALID_DIGEST_LEN`).

## 7. Проверка подписи

`VerifyData(Алиас, Флаги, Данные, Подпись, ВыходныеДанные ↩, Информация ↩, ИдСертификата, Сертификат ↩)` → Код  
`VerifyDataResult(Алиас, Флаги, Данные, Подпись)` → Строка «Информация» (пусто при ошибке).

Флаги: `KC_SIGN_CMS` либо `KC_SIGN_DRAFT`; формат `Подписи` — `KC_IN_BASE64`, `KC_IN_PEM`, `KC_IN_DER` (без флага PEM
определяется автоматически); `KC_DETACHED_DATA` — проверять подпись над переданными в `Данные` данными (даже если CMS содержит собственное содержимое);
без этого флага для CMS используется вложенное содержимое, а `Данные` игнорируется, и отделённая подпись без флага даёт `0x2E06307F` («нет содержимого»);
`KC_IN2_BASE64` — переданные данные в Base64 (RAW или с `KC_DETACHED_DATA`); `KC_OUT_BASE64` — вернуть вложенные данные в Base64; `KC_NOCHECKCERTTIME`.

`ВыходныеДанные` — содержимое вложенной CMS; `Информация` — отчёт вида
```
Signature N 1
- CAdES-BES: verify signer certificate hash - OK.
Verify - OK
CMS Verify - OK
```
`ИдСертификата` — номер подписи (с 1), чей сертификат вернуть в `Сертификат` (0 — не возвращать).
Для RAW-подписи проверка идёт сертификатом загруженного ключа либо загруженным как `KC_CERT_USER`.

Отсутствие данных при `KC_DETACHED_DATA` — `KCR_VERIFY_NODATA`. Коды: `0x8006E07B` — RAW-подпись не сходится, `0x2E09A09E` — CMS-подпись не сходится, `KCR_NOSIGNFOUND`, `KCR_VERIFY_NODATA`
(detached без данных), `KCR_UNKNOWN_CMS_FORMAT`, `KCR_CACERTNOTFOUND`, `KCR_CERTTIMEINVALID`.

**Как у Калкана:** правила данных для вложенной/отделённой подписи, отчёт проверки, коды OpenSSL, `KCR_NOSIGNFOUND`, `KCR_VERIFY_NODATA`, обязательность издателя в хранилище.
**Отличие:** при любых сочетаниях флагов и данных компонента возвращает код ошибки (Калкан на некоторых несогласованных сочетаниях аварийно завершает процесс).

### GetCertFromCMS (№ 53), GetTimeFromSig (№ 51)

`GetCertFromCMS(CMS, НомерПодписи, Флаги)` → Строка/BLOB: сертификат подписанта (`Флаги`: формат ввода `KC_IN_BASE64/PEM/DER`, вывода `KC_OUT_*`).  
`GetTimeFromSig(CMS, Флаги, НомерПодписи)` → строка с временем (Unix-секунды) из штампа TSA; без штампа — пустая строка и ошибка.

## 8. XML (XMLDSig)

`SignXML(Алиас, Флаги, ИдУзла, РодительскийУзел, ПространствоИмён, XML, Подпись ↩)` → Код  
`SignXMLResult(Алиас, Флаги, ИдУзла, РодительскийУзел, ПространствоИмён, XML)` → Строка  
`SignXMLNative`, `SignXMLNativeResult` — те же методы под вторым именем.

* `XML` — строка 1С (в UTF-8) или `ДвоичныеДанные` (разбирается как есть; в результате — тоже BLOB-совместимый текст).
* `ИдУзла` — значение атрибута `Id` или `ID` узла, на который ссылается подпись; пусто — весь документ.
* `РодительскийУзел` (+`ПространствоИмён`) — имя элемента, в который вставляется `ds:Signature`; пусто — корень документа.
* Алгоритм канонизации — флагом: `KC_XML_INCL_C14N` (по умолчанию), `…_C14NCOMMENT`, `…_C14N11`, `…_C14N11COMMENT`,
  `KC_XML_EXCL_C14N`, `…_EXCL_C14NCOMMENT` — для ссылки (младшие флаги) и `KC_XMLC_*` — для `SignedInfo`.
* Алгоритмы подписи и хэша выбираются по ключу: ГОСТ 2015-256/512 → `gostr34102015-gostr34112015-256/512`, ГОСТ 2001, RSA-SHA256.

`VerifyXML(Алиас, Флаги, XML, Информация ↩)` → Код; `VerifyXMLResult(Алиас, Флаги, XML)` → Строка.
Проверяются все подписи документа (digest, подпись, цепочка, срок). Отчёт — по подписи:
```
Signature N 1
Id = …
<серийный номер сертификата>
<алгоритм подписи сертификата>
<ИИН>
Signature is OK
```
Коды: `KCR_XMLPARSEERROR`, `KCR_NOSIGNFOUND` (нет подписи), `KCR_SIGN_INVALID`, `KCR_LOADTRUSTEDCERTSERR` (не загружены доверенные
сертификаты), `KCR_CACERTNOTFOUND`, `KCR_CERTTIMEINVALID`.

`GetCertFromXML(XML, НомерПодписи)` → сертификат подписанта (Base64); `GetSigAlgFromXML(XML)` → URI алгоритма подписи;
`XMLFinalize()` → `0` (совместимость).

**Как у Калкана:** структура `ds:Signature` (проверено до символа), флаги канонизации, вставка в родительский элемент, отчёт `VerifyXML`, коды `0x08F00022`…`0x08F00029`.
**Отличия:** несколько элементов с одним `Id` — ошибка подписи (`0x08F00027`, как у Калкана) и недействительная ссылка при проверке; документ с готовой «заготовкой» подписи
не подписывается; подпись узла, содержащего место вставки, получает `enveloped-signature` и проверяется; бит `0x100` не трактуется как `KC_WITH_TIMESTAMP`.
