# NEKalkan — электронная подпись НУЦ РК в 1С без внешних библиотек

**NEKalkan** — внешняя компонента для 1С:Предприятия (Native API, 64-разрядный Windows). Она подписывает и проверяет данные
по алгоритмам Республики Казахстан и не требует ничего, кроме себя самой: ни `KalkanCrypt.dll`, ни NCALayer, ни установки
SDK НУЦ РК на рабочие места, ни временных файлов с ключами.

* **Алгоритмы:** ГОСТ 34.10-2015 с хэшем Стрибог (256 и 512 бит), RSA-SHA256, хэши Стрибог, ГОСТ 34.11-94, SHA-256.
* **Форматы:** PKCS#12, X.509, CMS/CAdES-BES (вложенная и отделённая подпись, несколько подписей), «сырая» подпись (RAW),
  XMLDSig с канонизацией C14N 1.0/1.1/Exclusive.
* **Один файл:** `NEKalkan.dll`, около 240 КБ (у `KalkanCrypt.dll` — около 5 МБ). Зависит только от системных `KERNEL32` и `ADVAPI32`.
* **Свой контекст у каждого объекта:** два объекта с разными ключами в одном процессе не мешают друг другу.
* **Интерфейс как у Калкана:** те же названия методов (`SignData`, `VerifyData`, `SignXML`, `HashData` …), те же флаги и константы
  `KC_*`, те же коды ошибок `KCR_*`, те же тексты отчётов проверки. Код, привыкший к Калкану, переносится почти без изменений.

> NEKalkan — независимая реализация, а не продукт НУЦ РК, и она не проходила сертификацию как СКЗИ
> (см. «Ограничения и безопасность»). Где закон требует сертифицированное средство, используйте КалканКрипт НУЦ РК.

## Возможности

| Возможность | Состояние |
|---|---|
| Загрузка ключа из контейнера PKCS#12 (ГОСТ 2015 любой длины, RSA); порядок байт закрытого ключа определяется автоматически | ✅ |
| Подпись **CMS / CAdES-BES**: вложенная и отделённая, сертификат в подписи, `signingCertificateV2`, несколько подписей в одном CMS | ✅ |
| **RAW**-подпись (чистая подпись ГОСТ 34.10 / RSA) и подпись готового хэша (`SignHash`) | ✅ |
| Проверка CMS и RAW: подпись, цепочка до корня НУЦ, срок действия, `CAdES-BES` | ✅ |
| Подпись и проверка **XML (XMLDSig)**: C14N 1.0/1.1/Exclusive с комментариями и без, выбор подписываемого узла и места вставки, несколько подписей | ✅ |
| Хэширование: Стрибог-256/512, ГОСТ 34.11-94, SHA-256 (данные строкой, Base64, файлом) | ✅ |
| Свойства сертификата (`KC_CERTPROP_*`), экспорт сертификата в DER/PEM/Base64 | ✅ |
| Проверка сертификата: цепочка и срок (`KC_USE_NOTHING`), отзыв по CRL из файла (`KC_USE_CRL`) | ✅ |
| Время подписи из метки TSA (`GetTimeFromSig`) | ✅ чтение |
| Запрос метки времени, OCSP и загрузка CRL по сети, `SignWSSE`, `ZipConSign`/`ZipConVerify`, токены и ID-карты | ⏳ не входят в версию 1.0 |
| Ключи ГОСТ 34.10-2001 («2004») для подписи | ❌ не поддерживаются; такие подписи можно **проверять** |

## Сравнение с оригинальным Калканом

NEKalkan проверялся против настоящей `KalkanCrypt.dll` из SDK НУЦ РК 2.0 на тысячах сочетаний входных данных: подпись одного
всегда проверяется другим, а коды возврата и тексты отчётов совпадают. Полное сравнение — в
[docs/СРАВНЕНИЕ_С_КАЛКАНОМ.md](docs/СРАВНЕНИЕ_С_КАЛКАНОМ.md). Главное:

| | Оригинальный Калкан | NEKalkan |
|---|---|---|
| Поставка | `KalkanCrypt.dll` ≈ 5 МБ + настройка SDK на каждом рабочем месте | один файл ≈ 240 КБ внутри пакета компоненты |
| Состояние | общее на весь процесс: ключ и сертификаты одни на всех | отдельный контекст у каждого объекта |
| Пути к файлам | только однобайтовые (ASCII); ключ в папке с кириллицей приходится копировать | любые: Unicode, длиннее 260 символов; на диск ничего не пишется |
| Совместимость подписей | — | CMS и RAW-подписи, XML-подписи (структура подписи побайтно та же, значения разные) проверяются Калканом, и наоборот |
| Коды ошибок и тексты | `KCR_*`, коды OpenSSL, отчёты вида `Signature N 1 … Verify - OK` | те же, включая `0x8006E07B`, `0x2E09A09E` и формулировки отчётов |
| Скорость (ГОСТ 512, на одном ядре) | CMS: подпись 3,0 мс, проверка 4,2 мс; XML: подпись 3,1 мс, проверка 12,1 мс; Стрибог-512 30 МБ — 158 мс | CMS: подпись 5,3 мс, проверка 6,5 мс; XML: подпись 5,3 мс, проверка 6,5 мс; Стрибог-512 30 МБ — 144 мс |
| Неверные флаги и мусор на входе | возможен аварийный выход из процесса (например, `VerifyData` с несогласованными флагами и данными) | всегда код ошибки; проверено фаззингом и тестами враждебных входов |
| Проверка цепочки | при одном промежуточном сертификате без корня подписывает и проверяет | требует корневой сертификат (`KCR_CHECKCHAINERROR`) |
| Токены, ID-карты, OCSP/TSA по сети, WSSE, ZIP-контейнеры | есть | не входят в версию 1.0 |
| Ключи ГОСТ 2001 | подпись и проверка | только проверка |

## Подключение

1. В конфигурации (или внешней обработке) создайте **макет** типа «Двоичные данные» и загрузите в него
   `NEKalkan_win64.zip`, например общий макет `NEKalkanКомпонента`.
2. Подключите компоненту на **клиенте** (или на сервере) и создайте объект:

```bsl
&НаКлиенте
Функция СоздатьКрипто()
	Подключена = ПодключитьВнешнююКомпоненту("ОбщийМакет.NEKalkanКомпонента", "NEK",
		ТипВнешнейКомпоненты.Native, ТипПодключенияВнешнейКомпоненты.НеИзолированно);
	Если Не Подключена Тогда
		ВызватьИсключение "Не удалось подключить компоненту NEKalkan";
	КонецЕсли;
	Возврат Новый("AddIn.NEK.NEKalkan");
КонецФункции
```

Имя класса — `NEKalkan`. Если код уже написан под Калкан с классом `KalkanCrypt`, достаточно заменить
`AddIn.<имя>.KalkanCrypt` на `AddIn.<имя>.NEKalkan`.

Требуется платформа 1С:Предприятие **8.3.13** или новее и 64-разрядный клиент (или сервер). Режим подключения — `НеИзолированно`.
При первом подключении из внешней обработки платформа спросит разрешение на запуск бинарного файла — это обычное поведение
платформы для внешних модулей; из конфигурации запрос не появляется.

## Быстрый старт

```bsl
Крипто = СоздатьКрипто();

Если Крипто.Init() <> Крипто.KCR_OK Тогда
	ВызватьИсключение Крипто.GetLastErrorFull();
КонецЕсли;
Крипто.SetStringEncoding("UTF-8");

// 1. Доверенные сертификаты НУЦ (корневой и промежуточный) — один раз для объекта.
Крипто.X509LoadCertificateFromFile("C:\НУЦ\root_gost_2022.cer", Крипто.KC_CERT_CA);
Крипто.X509LoadCertificateFromFile("C:\НУЦ\nca_gost_2022.cer",  Крипто.KC_CERT_INTERMEDIATE);

// 2. Ключ пользователя.
Код = Крипто.LoadKeyStore(Крипто.KCST_PKCS12, ПарольКлюча, "C:\Ключи\GOST512_xxx.p12", "");
Если Код <> Крипто.KCR_OK Тогда
	ВызватьИсключение Крипто.GetLastErrorFull();
КонецЕсли;

// 3. Подпись CMS (вложенная), результат — Base64.
Подпись = Крипто.SignDataResult("", Крипто.KC_SIGN_CMS + Крипто.KC_OUT_BASE64, "Договор №15", "");

// 4. Проверка.
Инфо = Крипто.VerifyDataResult("", Крипто.KC_SIGN_CMS + Крипто.KC_IN_BASE64, "", Подпись);
Если Инфо = "" Тогда
	Сообщить("Подпись неверна: " + Крипто.GetLastErrorFull());
Иначе
	Сообщить(Инфо);   // «Signature N 1 ... CMS Verify - OK»
КонецЕсли;
```

Больше примеров — в каталоге `examples/`.

## Корневые и промежуточные сертификаты НУЦ

Подпись, проверка и `VerifyXML` работают только если в объекте загружены **доверенные сертификаты** — корневой (`KC_CERT_CA`)
и промежуточный (`KC_CERT_INTERMEDIATE`) удостоверяющие центры, выдавшие сертификат ключа. Без них NEKalkan вернёт `KCR_CACERTNOTFOUND`
(`0x08F00040`) — так же, как оригинальный Калкан. Системное хранилище Windows не используется: сертификаты загружаются явно, один раз на объект.
Файлы сертификатов НУЦ РК (`root_gost_2022.cer`, `nca_gost_2022.cer`, для RSA — `root_rsa_2020.cer`, `nca_rsa_2022.cer`) скачиваются
с https://pki.gov.kz (например, `http://pki.gov.kz/cert/nca_gost_2022.cer`).

Из файлов на диске:

```bsl
Крипто.X509LoadCertificateFromFile("C:\НУЦ\root_gost_2022.cer", Крипто.KC_CERT_CA);            // корневой
Крипто.X509LoadCertificateFromFile("C:\НУЦ\nca_gost_2022.cer",  Крипто.KC_CERT_INTERMEDIATE); // промежуточный (НУЦ)
```

Из макетов конфигурации (рекомендуется: сертификаты поставляются вместе с решением, на клиенте не нужны файлы).
Создайте макеты типа «Двоичные данные» `КорневойСертификатНУЦ` и `ПромежуточныйСертификатНУЦ` и загрузите в них `.cer`.
`ПолучитьОбщийМакет` вызывается на сервере; на клиент передайте полученные `ДвоичныеДанные` параметром серверной функции:

```bsl
Процедура ЗагрузитьДоверенныеСертификаты(Крипто)

	Корневой = ПолучитьОбщийМакет("КорневойСертификатНУЦ");           // ДвоичныеДанные
	Промежуточный = ПолучитьОбщийМакет("ПромежуточныйСертификатНУЦ");

	// X509LoadCertificateFromBuffer принимает DER, PEM или Base64 — строкой или двоичными данными.
	Код = Крипто.X509LoadCertificateFromBuffer(Корневой, Крипто.KC_CERT_CA);
	Если Код <> Крипто.KCR_OK Тогда
		ВызватьИсключение "Корневой сертификат НУЦ не загружен: " + Крипто.GetLastErrorFull();
	КонецЕсли;

	Код = Крипто.X509LoadCertificateFromBuffer(Промежуточный, Крипто.KC_CERT_INTERMEDIATE);
	Если Код <> Крипто.KCR_OK Тогда
		ВызватьИсключение "Промежуточный сертификат НУЦ не загружен: " + Крипто.GetLastErrorFull();
	КонецЕсли;

КонецПроцедуры
```

Если пользователи работают с ключами разных поколений, загрузите все нужные пары — по одной на каждую цепочку
(например, ГОСТ 2022 и RSA): лишние сертификаты не мешают, повторная загрузка того же сертификата безвредна.
Проверить, что сертификат пользователя доходит до загруженного корня, можно до подписи:

```bsl
Сертификат = Крипто.ExportCertificate("", Крипто.KC_CERT_B64);           // сертификат загруженного ключа
Крипто.X509ValidateCertificateResult(Сертификат, Крипто.KC_USE_NOTHING, "", 0);
Если Крипто.GetLastError() <> 0 Тогда
	// KCR_CACERTNOTFOUND — нет издателя в хранилище; KCR_CHECKCHAINERROR — нет корня; KCR_CERTTIMEINVALID — срок истёк
	ВызватьИсключение Крипто.GetLastErrorFull();
КонецЕсли;
```

## Как устроен прикладной интерфейс

Каждая операция представлена в **двух формах**, как и у Калкана для 1С:

* процедурная — возвращает число (код `KCR_*`), результат кладёт в параметр-ссылку:
  `Код = Крипто.SignData("", Флаги, Данные, Результат);`
* «Результатом» — возвращает значение сразу, при ошибке — пустую строку, причину смотрите в
  `GetLastErrorFull()`: `Подпись = Крипто.SignDataResult("", Флаги, Данные, "");`

Имена методов доступны по-английски и по-русски (`SignData` / `ПодписатьДанные`), полный перечень — `GetMethodList()`.
Все константы `KC_*`, `KCR_*`, `KCST_*` доступны как свойства объекта: `Крипто.KC_SIGN_CMS` (список — `GetPropertyList()`).
Служебные имена `GetWrapperVersion` и `WRAP_*` сохранены ради переносимости кода, который привык к ним.

## Кодировка строк

Строки 1С передаются в компоненту в **UTF-8** (по умолчанию) — именно эти байты хэшируются и подписываются.
Метод `SetStringEncoding` переключает кодировку обмена: `UTF-8`, `CP1251` (`1251`), `ACP`.

Имена файлов, пароли, алиасы и XML всегда передаются как Unicode (в UTF-8), независимо от этой настройки.
Строка, которую нельзя представить в выбранной кодировке, приводит к ошибке `WRAP_CONVERSION_ERROR`, а не к молчаливой
замене букв на «?» перед подписью. Двоичные данные передавайте типом `ДвоичныеДанные` — они не перекодируются.

> **Отличие от Калкана для 1С:** там кодировка по умолчанию — `ACP` (в русской Windows это CP1251).
> Если ваш код подписывал строки с кириллицей, не вызывая `SetStringEncoding`, подпись была по байтам CP1251;
> чтобы получить прежний результат, вызовите `Крипто.SetStringEncoding("CP1251")`. Для новых решений рекомендуется UTF-8.

## Коды ошибок

Коды `KCR_*` совпадают с SDK НУЦ РК (`0x08F00000 + N`), коды самой компоненты `WRAP_*` — `0x0A510000 + N`.
При ошибке проверки подписи возвращаются коды OpenSSL, как у Калкана (например, `0x8006E07B` — неверная подпись ГОСТ,
`0x2E09A09E` — неверная CMS-подпись). Имя кода — `GetErrorName(Код)`, полное описание последней ошибки —
`GetLastErrorFull()`, текст — `GetLastErrorText()`.

Ошибки вызова компоненты (`WRAP_*`: неверное число или тип параметров, не удалось выделить память, метод не
реализован) дополнительно записываются в журнал регистрации через `AddError`; ошибки криптографии (`KCR_*`)
возвращаются только кодом — как у Калкана.

## Ограничения и безопасность

* **Не сертифицирована** как средство криптографической защиты информации; не является продуктом НУЦ РК.
* Закрытый ключ после `LoadKeyStore` хранится в памяти объекта; пароль и промежуточные буферы затираются.
  Ключ **не** записывается на диск. `Finalize` и освобождение объекта затирают ключ и сертификаты.
* Подпись ГОСТ 34.10 использует случайное `k` от генератора ОС (`RtlGenRandom`). Арифметика эллиптических кривых не защищена от атак
  по времени и кэшу: используйте компоненту там, где подпись выполняется в доверенной среде.
* Проверка отвергает ключи малого порядка (проверка подгруппы), RSA-экспоненты `e < 3`, неоднозначные ссылки `Id` в XML.
* CMS `CAdES-T` (метка времени) читается, но не создаётся.
* **`VerifyXML` подтверждает целостность узлов, на которые ссылается подпись, и действительность сертификата — но не говорит, *какой именно* узел подписан.**
  Подписанный элемент можно перенести в другое место документа (XML Signature Wrapping), и подпись останется верной. Если документ разбирается
  вашим кодом, убедитесь, что значимые данные берутся из подписанного узла (например, подпись ссылается на `#id` нужного элемента, и вы читаете именно его),
  а ссылка `URI=""` означает «весь документ».
* Один объект компоненты — один поток.

## Сборка

Нужен только LLVM для Windows (`clang++`, `lld-link`); сторонних библиотек и Windows SDK не требуется.

```powershell
powershell -File tools\build.ps1        # out\NEKalkan.dll — боевая компонента
powershell -File tools\package.ps1      # out\NEKalkan_win64.zip — пакет для макета 1С (MANIFEST.XML + DLL)
```

Готовый пакет `NEKalkan_win64.zip` опубликован в разделе Releases. Как проверялась реализация (сверка с оригинальной `KalkanCrypt.dll`,
фаззинг, поиск утечек) описано в `docs/ТЕХНИЧЕСКОЕ.md`.
